## The Manual Way

In Module 4, `broken/start_broken_system.sh` started the system with a bash script:

```bash
ros2 run turtlesim turtlesim_node &
sleep 1
ros2 run goal_point_publisher goal_point_publisher &
sleep 1
ros2 run turtlesim_controller turtle_lf_controller_broken &
sleep 2
ros2 lifecycle set /turtle_lf_controller_broken configure
ros2 lifecycle set /turtle_lf_controller_broken activate
```

It works, but the `sleep` calls guess how long each node takes to start. A slow machine breaks it; a fast one wastes time. A launch file can instead **react to the node's actual state**: activate when configure has finished.

## Concept: `LifecycleNode` and Transition Events

`LifecycleNode` replaces `Node` for a lifecycle node. It starts the node in `unconfigured` and lets launch send transitions to it:

```python
from launch_ros.actions import LifecycleNode

controller = LifecycleNode(
    package='turtlesim_controller',
    executable='turtle_lf_controller',
    name='turtle_lf_controller',
    namespace='',
    output='screen',
)
```

`namespace` is **required** for `LifecycleNode` (use `''` for none).

A transition is requested by emitting a `ChangeState` event:

```python
from launch.actions import EmitEvent
from launch.events import matches_action
from launch_ros.events.lifecycle import ChangeState
from lifecycle_msgs.msg import Transition

configure = EmitEvent(event=ChangeState(
    lifecycle_node_matcher=matches_action(controller),
    transition_id=Transition.TRANSITION_CONFIGURE,
))
```

To run `activate` *after* the node reaches `inactive`, register a handler that watches the node's state changes:

```python
from launch.actions import RegisterEventHandler
from launch_ros.event_handlers import OnStateTransition

activate_after_configure = RegisterEventHandler(OnStateTransition(
    target_lifecycle_node=controller,
    goal_state='inactive',
    entities=[EmitEvent(event=ChangeState(
        lifecycle_node_matcher=matches_action(controller),
        transition_id=Transition.TRANSITION_ACTIVATE,
    ))],
))
```

Read it as: *when the controller arrives in state `inactive`, emit the activate transition.* `goal_state='inactive'` is the state reached by `configure`.

**Order matters.** Put the `RegisterEventHandler` in the `LaunchDescription` list **before** the `configure` event. If configure runs first and finishes before the handler exists, the transition to `inactive` is missed and the node never activates.

## Step 1 — Write the Launch File

Create `launch/lifecycle_demo.launch.py`:

```python
from launch import LaunchDescription
from launch.actions import (
    EmitEvent, IncludeLaunchDescription, RegisterEventHandler)
from launch.events import matches_action
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch.substitutions import PathJoinSubstitution
from launch_ros.actions import LifecycleNode
from launch_ros.event_handlers import OnStateTransition
from launch_ros.events.lifecycle import ChangeState
from launch_ros.substitutions import FindPackageShare
from lifecycle_msgs.msg import Transition


def generate_launch_description():
    sim = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            PathJoinSubstitution([
                FindPackageShare('turtlesim_controller'),
                'launch',
                'sim.launch.py',
            ])
        ),
    )

    controller = LifecycleNode(
        package='turtlesim_controller',
        executable='turtle_lf_controller',
        name='turtle_lf_controller',
        namespace='',
        output='screen',
        parameters=[{'Kv': 1.0, 'Kw': 5.0, 'tolerance': 0.1}],
    )

    activate_after_configure = RegisterEventHandler(OnStateTransition(
        target_lifecycle_node=controller,
        goal_state='inactive',
        entities=[EmitEvent(event=ChangeState(
            lifecycle_node_matcher=matches_action(controller),
            transition_id=Transition.TRANSITION_ACTIVATE,
        ))],
    ))

    configure = EmitEvent(event=ChangeState(
        lifecycle_node_matcher=matches_action(controller),
        transition_id=Transition.TRANSITION_CONFIGURE,
    ))

    return LaunchDescription([
        sim,
        controller,
        activate_after_configure,   # handler first ...
        configure,                  # ... then the first transition
    ])
```

Build and launch:

```bash
cd ~/tutorial_ws
colcon build --packages-select turtlesim_controller
source ~/tutorial_ws/install/setup.bash
ros2 launch turtlesim_controller lifecycle_demo.launch.py
```

Watch the terminal: the controller logs `Configured.` and then `Activated — control loop enabled.` without any manual command. In a second terminal:

```bash
ros2 lifecycle get /turtle_lf_controller
# active [3]
```

Click a point in the goal GUI: the turtle drives to it.

## Step 2 — Prove the Ordering Rule

Swap the last two list items so `configure` comes first:

```python
    return LaunchDescription([
        sim,
        controller,
        configure,
        activate_after_configure,
    ])
```

Rebuild and relaunch. The result can vary: on a fast start the controller stays in `inactive` and the turtle ignores the goal, while on a slow start it still works. That intermittency is the reason to always register the handler first. Restore the original order.

Add a second handler so the controller **deactivates** when the goal GUI exits. Use `OnProcessExit` from `launch.event_handlers` (5.9).

## Answer Key

```python
from launch.actions import EmitEvent, RegisterEventHandler
from launch.event_handlers import OnProcessExit
from launch_ros.actions import Node

    turtlesim_node = Node(
        package='turtlesim',
        executable='turtlesim_node',
        name='turtlesim',
        output='screen',
    )

    goal_gui = Node(
        package='goal_point_publisher',
        executable='goal_point_publisher',
        name='goal_point_publisher',
        output='screen',
    )

    deactivate_on_gui_exit = RegisterEventHandler(OnProcessExit(
        target_action=goal_gui,
        on_exit=[EmitEvent(event=ChangeState(
            lifecycle_node_matcher=matches_action(controller),
            transition_id=Transition.TRANSITION_DEACTIVATE,
        ))],
    ))
```

Replace `sim` in the `LaunchDescription` list with `turtlesim_node` and `goal_gui`, and add `deactivate_on_gui_exit`. `OnProcessExit` fires when the target process ends, and `on_exit` lists the actions to run then. This is the same event-handler pattern as before, with a different trigger: launch reacts to things that happen instead of waiting a fixed time.

---

## Summary

| Concept | Key point |
|---|---|
| `LifecycleNode` | Like `Node`, but starts in `unconfigured`; `namespace` is required |
| `EmitEvent(ChangeState(...))` | Requests a lifecycle transition |
| `matches_action(node)` | Selects which node the event targets |
| `OnStateTransition(goal_state=...)` | Runs its `entities` once the node reaches that state |
| Ordering | Register the handler before emitting the transition it waits on |
