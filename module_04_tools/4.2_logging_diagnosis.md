## The /rosout Topic

Every ROS2 node publishes log messages to the `/rosout` topic. Each message is of type `rcl_interfaces/msg/Log`:

```
uint8 level        # 10=DEBUG, 20=INFO, 30=WARN, 40=ERROR, 50=FATAL
string name        # node's logger name (usually the node name)
string msg         # the log message text
string file        # source file that called the logger
string function    # function name
uint32 line        # line number
```

You can inspect raw log messages with:

```bash
ros2 topic echo /rosout
```

In practice, `ros2 topic echo /rosout` is difficult to read when multiple nodes are running — messages from all nodes arrive interleaved. `rqt_console` is the right tool for multi-node logging.

## rqt_console

`rqt_console` subscribes to `/rosout` and displays messages in a filterable table. Open it in a new terminal:

```bash
rqt_console
```

**Interface:**

- Each row is one log message: timestamp, severity, node name, message, file, and line
- The **Filter** box at the top narrows to messages matching a substring
- Click **Add** next to Exclude Filters to permanently hide noisy messages (e.g., hide `turtlesim_node` to focus on your controller)
- The **Severity** column is color-coded: green = INFO, yellow = WARN, red = ERROR

**Important limitation:** `rqt_console` has no history of messages published before it launched. If a node logged an ERROR during startup and then crashed, `rqt_console` will not show it unless you had it open at the time. For startup errors, run `rqt_console` before starting the nodes.

## Runtime Log Level Changes

By default, most nodes publish at INFO level or higher. DEBUG messages are suppressed — they would flood `/rosout` in production. You can change the level of any running node's logger without restarting it:

```bash
ros2 service call /NODE_NAME/set_logger_levels \
  rcl_interfaces/srv/SetLoggerLevels \
  "{levels: [{name: 'NODE_NAME', level: 10}]}"
```

Log level numbers:

| Level | Number |
|---|---|
| DEBUG | 10 |
| INFO | 20 |
| WARN | 30 |
| ERROR | 40 |
| FATAL | 50 |

Setting level 10 (DEBUG) makes the node publish all internal debug messages. To restore INFO level, call the same service with `level: 20`.

**Node name vs. logger name:** The `name` field in the `levels` list must match the node's logger name, which is usually the same as the node name returned by `ros2 node list`. Capitalization matters. If the call succeeds silently but nothing changes, check the name with `ros2 node list`.

## ros2 doctor

`ros2 doctor` runs a suite of system-level checks and reports any configuration problems it finds:

```bash
ros2 doctor
```

A brief pass/fail summary appears. For the full report with details on every check:

```bash
ros2 doctor --report
```

Checks include:

- ROS environment variables (`ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`, `ROS_LOCALHOST_ONLY`)
- DDS implementation detected
- Available network interfaces
- Packages installed vs. expected
- `ROS_DISTRO` consistency

`ros2 doctor` is a first-pass diagnostic. Run it when:
- Nodes cannot discover each other (domain ID mismatch)
- You installed a new package and something stopped working
- You are setting up a new machine and want a baseline check

It does not diagnose runtime communication problems (QoS mismatches, dropped messages) — those are covered in 4.3.

## Exercise 1 — rqt_console and Log Level

**Description**

With the full system running and `turtle_controller` enabled:

1. Open `rqt_console` before starting the exercise.
2. Click several goal points in the goal publisher window. Watch `rqt_console` populate with INFO messages from `turtle_controller`.
3. Disable the controller and observe how the log output changes:
   ```bash
   ros2 service call /controller_enabled std_srvs/srv/SetBool "{data: false}"
   ```
   Click a goal — the turtle no longer moves, and the controller should log that it is disabled (depending on your implementation).
4. Re-enable the controller:
   ```bash
   ros2 service call /controller_enabled std_srvs/srv/SetBool "{data: true}"
   ```
5. Send an out-of-range parameter (the controller's parameter callback should log a WARNING):
   ```bash
   ros2 param set /turtle_controller Kv -1.0
   ```
   If no WARN appears, the controller does not validate parameters — note this for later.
6. Enable DEBUG logging on the controller:
   ```bash
   ros2 service call /turtle_controller/set_logger_levels \
     rcl_interfaces/srv/SetLoggerLevels \
     "{levels: [{name: 'turtle_controller', level: 10}]}"
   ```
   Click a goal and observe the new DEBUG messages in `rqt_console`. Use the Filter box to show only messages from `/turtle_controller`.

**Verification**

- INFO messages from `turtle_controller` appear immediately on startup (it subscribes and logs from the start)
- After setting level 10, DEBUG messages appear that were not visible before
- The Filter box in `rqt_console` can isolate messages from a single node

## Exercise 2 — ros2 doctor

**Description**

1. Stop all nodes. Run `ros2 doctor` with nothing running. Note which warnings appear.
2. Start only `turtlesim_node`. Run `ros2 doctor` again. Note which warnings changed.
3. Run `ros2 doctor --report` and read the DDS section. Identify which DDS implementation is in use.
4. Check the current value of `ROS_DOMAIN_ID`:
   ```bash
   echo $ROS_DOMAIN_ID
   ```
   If it is empty, the default (domain 0) is in use. If you change it in one terminal and not another, the nodes in those terminals cannot discover each other. `ros2 doctor` will flag this as a warning.

**Verification**

- `ros2 doctor --report` shows a non-empty DDS implementation name
- You can explain what `ROS_DOMAIN_ID` does (covered in 1.9) and why `ros2 doctor` flags mismatches

## Answer Key

### Exercise 1

`turtle_controller` logs at INFO level immediately on startup — it subscribes and begins processing as soon as the node starts. INFO messages appear in `rqt_console` as the controller receives pose and goal updates.

After setting level 10 (DEBUG), the logger threshold drops and messages that were previously suppressed become visible. These include rclpy internals as well as any `self.get_logger().debug(...)` calls in your node. This is the key insight: DEBUG logging is always happening inside the node; the threshold controls what gets sent to `/rosout`.

For the parameter set call: if your controller validates `Kv` in the parameter callback and rejects negative values, a WARN appears. If it accepts any value, no WARN appears. Neither is wrong — it depends on your implementation.

### Exercise 2

`ros2 doctor` with no nodes running typically warns about:
- No nodes discovered (expected)
- Possibly a RMW implementation note

With `turtlesim_node` running, some warnings about missing nodes may clear. The DDS section of `--report` shows the RMW implementation (e.g., `rmw_fastrtps_cpp` for Fast-DDS, which is the Humble default).

`ROS_DOMAIN_ID` defaults to 0 when unset. All terminals in a session share the same environment if you source the same shell — but if you open a new terminal with a different `ROS_DOMAIN_ID`, nodes in that terminal are invisible to nodes in others. `ros2 doctor` catches this.

## Summary

| Tool | Purpose | Key limitation |
|---|---|---|
| `rqt_console` | Multi-node log viewer with filtering | No history — must be open before the event |
| `/rosout` | The topic all node loggers publish to | Raw; hard to read without rqt_console |
| `set_logger_levels` | Runtime log level change | Node name must match exactly |
| `ros2 doctor` | System-level config checks | Does not diagnose runtime communication |
| `ros2 doctor --report` | Full system report | Read DDS + network sections first |
