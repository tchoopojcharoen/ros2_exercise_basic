# 4.9 — Capstone: Debugging a Broken System

## Learning Objectives

By the end of this section, you will be able to:
- Apply the tools from sections 4.1–4.3 to diagnose a non-working ROS2 system
- Identify communication problems using `rqt_graph`, `ros2 node info`, and `ros2 topic info --verbose`
- Fix two independent bugs and verify the system works correctly after each fix

---

## Before You Begin

This section uses a broken version of the go-to-goal controller. You will add it to your `turtlesim_controller` package and run it.

You need:

- `turtlesim_controller` built and sourced in `~/tutorial_ws`
- Access to `module_04_tools/broken/` from this repository

Open three terminals and source the workspace in each:


## The Scenario

The system appears to start correctly:

- `turtlesim_node` is running and the turtlesim window opens
- `goal_point_publisher` is running and the GUI opens
- `turtle_lf_controller_broken` configures and activates without any error messages
- `ros2 lifecycle get /turtle_lf_controller_broken` shows `active`

But when you click goal points in the goal publisher window, **the turtle does not move**.

There are no crash messages. No ERROR or WARN in `rqt_console`. The system looks healthy from the outside.

Your job is to find and fix the bugs using only the tools from sections 4.1–4.3.

- Do not read `turtle_lf_controller_broken.py` to find the bugs. Use the diagnostic tools.
- Fix each bug one at a time. After each fix, rebuild and verify the system is partially or fully working before moving to the next.
- You may use: `rqt_graph`, `rqt_topic`, `rqt_console`, `ros2 node info`, `ros2 topic list`, `ros2 topic echo`, `ros2 topic info --verbose`.

**Starting questions:**

1. Open `rqt_graph`. Does the diagram show what you expect for a working go-to-goal system? What is missing or wrong?

2. Run `ros2 node info /turtle_lf_controller_broken`. Compare the subscription list to what you would expect for a correct controller. Is anything unexpected?

3. Is `/turtle1/pose` data arriving at the controller? Use `ros2 topic info --verbose /turtle1/pose` to check.

Work through the questions one at a time. Diagnose the first bug, fix it, rebuild, restart the system, and verify progress before looking for the next bug.

## Answer Key

Read this section only after you have made a genuine attempt at the exercise.

### Bug 1 — Wrong Goal Topic Name

**Diagnosis:**

`rqt_graph` shows that `goal_point_publisher` publishes to `/turtle1/goal`, but `turtle_lf_controller_broken` has no subscription connected to that topic. If you expand the graph to show all topics, you may see the controller subscribed to a topic that has no publisher.

`ros2 node info /turtle_lf_controller_broken` shows the subscription list:

```
  /turtle_lf_controller_broken/wrong_turtle/goal
```

Wait — the subscription is listed with the node's namespace prefix if it's a relative topic, or as an absolute path if you used `/`. Either way, it is not `/turtle1/goal`.

**Fix:**

In `turtle_lf_controller_broken.py`, locate the `goal_sub` creation in `on_configure`:

```python
self.goal_sub = self.create_subscription(
    Point,
    '/wrong_turtle/goal',   # <-- wrong
    self.goal_callback,
    10
)
```

Change the topic string to `'goal'` (relative, picks up the node's namespace):

```python
self.goal_sub = self.create_subscription(
    Point,
    'goal',                 # <-- correct
    self.goal_callback,
    10
)
```

Rebuild and restart. In `rqt_graph`, the arrow from `goal_point_publisher` to `turtle_lf_controller_broken` now appears. But the turtle still does not move — there is another bug.

---

### Bug 2 — QoS Mismatch on Pose Subscription

**Diagnosis:**

After fixing Bug 1, click a goal point. The controller receives the goal (`ros2 topic echo /turtle1/goal` shows data; `rqt_console` shows the "Goal received" log message). But the turtle still does not move.

Run `ros2 topic info --verbose /turtle1/pose`:

```
Topic: /turtle1/pose
Type: turtlesim/msg/Pose
Publisher count: 1
Subscription count: 2

Node name: turtlesim
...
  Reliability: BEST_EFFORT

Node name: turtle_lf_controller_broken
...
  Reliability: RELIABLE
  Matched publishers: 0        # <-- the controller has 0 matched publishers
```

The controller's pose subscription requests `RELIABLE` but the only publisher (`turtlesim_node`) uses `BEST_EFFORT`. A subscriber requesting RELIABLE is more demanding than what the publisher can guarantee — no match is made.

Without pose data, the controller's `control_loop` always calls `publish_zero_twist()` and returns early. The turtle never receives a nonzero command.

**Fix:**

In `turtle_lf_controller_broken.py`, locate the `pose_sub` creation in `on_configure`:

```python
from rclpy.qos import QoSProfile, ReliabilityPolicy

broken_qos = QoSProfile(
    depth=10,
    reliability=ReliabilityPolicy.RELIABLE,   # <-- wrong
)
self.pose_sub = self.create_subscription(
    Pose,
    'pose',
    self.pose_callback,
    broken_qos
)
```

Change to use the sensor data preset:

```python
from rclpy.qos import QoSPresetProfiles

self.pose_sub = self.create_subscription(
    Pose,
    'pose',
    self.pose_callback,
    QoSPresetProfiles.SENSOR_DATA.value    # <-- correct
)
```

Also remove the `broken_qos` variable and the import of `QoSProfile` and `ReliabilityPolicy` if they are no longer used (or keep them — the linter will warn about unused imports but the node will still run).

Rebuild and restart. After fixing Bug 2:

- `ros2 topic info --verbose /turtle1/pose` shows `Matched publishers: 1` for the controller's subscription
- Clicking a goal causes the turtle to navigate
- `ros2 topic echo /turtle1/cmd_vel` shows nonzero values

---

## What Made This Hard

Both bugs produced a **silent failure**: no crash, no error message in the terminal, and `ros2 lifecycle get` reported the controller as `active`. This is realistic — most ROS2 bugs do not announce themselves. The system appears to be running.

The key insight that this capstone illustrates:

- **Bug 1** (wrong topic) was visible in the *structure* of the graph — `rqt_graph` and `ros2 node info` showed the wrong topic name. No data needed to be flowing to diagnose it.
- **Bug 2** (wrong QoS) was invisible to the graph — the topic name was correct, the graph showed an arrow. Only `ros2 topic info --verbose` revealed the mismatch by showing `Matched publishers: 0`.

The four-step QoS diagnosis workflow from section 4.3 is exactly the right tool for Bug 2: confirm topic exists → confirm graph shows connection → confirm data is flowing (`ros2 topic echo`) → check matched publisher count.
