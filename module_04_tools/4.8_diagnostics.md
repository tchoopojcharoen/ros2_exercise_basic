## What are Diagnostics?

Diagnostics is a ROS2 convention for nodes to **self-report their health** at a standard location. Any node can publish status messages describing whether it is OK, WARN, or ERROR — without requiring a separate monitoring system to know how to inspect each node individually.

All status messages go to the `/diagnostics` topic with type `diagnostic_msgs/msg/DiagnosticArray`:

```
std_msgs/msg/Header header
diagnostic_msgs/msg/DiagnosticStatus[] status
```

Each `DiagnosticStatus` entry contains:

```
uint8 level          # 0=OK, 1=WARN, 2=ERROR, 3=STALE
string name          # human-readable identifier (e.g., "Pose Watchdog")
string hardware_id   # hardware identifier (e.g., "turtlesim")
string message       # short status description (e.g., "Pose received OK")
diagnostic_msgs/msg/KeyValue[] values  # optional key-value details
```

The level values as constants:

```python
from diagnostic_msgs.msg import DiagnosticStatus
DiagnosticStatus.OK    # 0
DiagnosticStatus.WARN  # 1
DiagnosticStatus.ERROR # 2
DiagnosticStatus.STALE # 3
```

## diagnostic_updater

Writing `/diagnostics` messages by hand is verbose. The `diagnostic_updater` package provides a `Updater` class that manages periodic publication and accumulates status from multiple tasks.

```python
from diagnostic_updater import Updater

updater = Updater(self)
updater.setHardwareID('turtlesim')
updater.add('My Check Name', self._check_function)
```

The updater publishes automatically when its internal timer fires (default: 1 Hz). `add()` registers a named diagnostic task — the updater calls `self._check_function` on every publish cycle. The task function receives a `DiagnosticStatusWrapper` and must call `stat.summary()` to set the level and message:

```python
def _check_function(self, stat):
    if self._condition_ok:
        stat.summary(DiagnosticStatus.OK, "Everything fine")
    else:
        stat.summary(DiagnosticStatus.WARN, "Problem detected")
    stat.add('detail_key', str(self._some_value))
    return stat
```

`stat.add(key, value)` appends a `KeyValue` entry to the status for extra detail (e.g., the actual measured value, or a timestamp).

## Package Dependencies

`diagnostic_updater` must be declared as a dependency in your package. In `package.xml`, add:

```xml
<depend>diagnostic_updater</depend>
```

And in `setup.py`, the Python package is available as `diagnostic_updater` — no additional entry needed there, but the `package.xml` dependency ensures `colcon` can find it.

## Worked Example — Pose Watchdog

The following node subscribes to `/turtle1/pose` and reports WARN on `/diagnostics` if no pose has been received within the last 2 seconds.

Create `~/tutorial_ws/src/turtlesim_controller/turtlesim_controller/health_reporter.py`:

```python
import time

import rclpy
from rclpy.node import Node
from rclpy.qos import QoSPresetProfiles
from turtlesim.msg import Pose

from diagnostic_msgs.msg import DiagnosticStatus
from diagnostic_updater import Updater


class HealthReporter(Node):
    def __init__(self):
        super().__init__('health_reporter')
        self._last_pose_time = None

        self.create_subscription(
            Pose,
            '/turtle1/pose',
            self._on_pose,
            QoSPresetProfiles.SENSOR_DATA.value,
        )

        self._updater = Updater(self)
        self._updater.setHardwareID('turtlesim')
        self._updater.add('Pose Watchdog', self._check_pose)

    def _on_pose(self, msg):
        self._last_pose_time = time.monotonic()

    def _check_pose(self, stat):
        if self._last_pose_time is None:
            stat.summary(DiagnosticStatus.WARN, 'No pose received yet')
        elif time.monotonic() - self._last_pose_time > 2.0:
            stat.summary(DiagnosticStatus.WARN, 'No pose received in >2 s')
        else:
            stat.summary(DiagnosticStatus.OK, 'Pose received OK')
        return stat


def main():
    rclpy.init()
    rclpy.spin(HealthReporter())
    rclpy.shutdown()
```

Add `health_reporter` to `console_scripts` in `setup.py`:

```python
'health_reporter = turtlesim_controller.health_reporter:main',
```

Add the dependency to `package.xml`:

```xml
<depend>diagnostic_updater</depend>
```

Build and source:

```bash
cd ~/tutorial_ws
colcon build --packages-select turtlesim_controller
source ~/tutorial_ws/install/setup.bash
```

## Reading Diagnostics

Start turtlesim and the health reporter:

**Terminal 1:**
```bash
ros2 run turtlesim turtlesim_node
```

**Terminal 2:**
```bash
ros2 run turtlesim_controller health_reporter
```

**Terminal 3 — read the diagnostics:**
```bash
ros2 topic echo /diagnostics
```

You should see output like:

```yaml
header:
  stamp:
    sec: 1704067201
    nanosec: 0
  frame_id: ''
status:
- level: "\0"          # 0 = OK
  name: 'health_reporter: Pose Watchdog'
  message: Pose received OK
  hardware_id: turtlesim
  values: []
```

Now kill `turtlesim_node` (`Ctrl+C` in Terminal 1). Wait 3 seconds. In Terminal 3, the next diagnostic output will show `level: "\x01"` (1 = WARN) and `message: No pose received in >2 s`.

## Exercise 2 — Optional: Parameter Bounds Check

**Description**

Add a second diagnostic task to `HealthReporter` that checks whether the `Kv` parameter of `turtle_lf_controller` is within a safe range.

You cannot query another node's parameters directly from within a diagnostic callback. Instead, create a parameter client in `HealthReporter.__init__` and poll the value periodically. For simplicity: use a `create_timer(2.0, ...)` callback that calls `ros2 param get /turtle_lf_controller Kv` via an async parameter client and stores the result.

Alternatively, approach this as a standalone "parameter watcher" node that uses `rclpy.parameter.client.AsyncParameterClient` or `ros2cli` under the hood.

A simpler version: read `Kv` from the `/turtle_lf_controller/get_parameters` service manually. If `Kv > 5.0`, report WARN "Kv gain is unusually high". If `0 < Kv <= 5.0`, report OK.

This exercise is open-ended — there are multiple valid approaches. The key learning goal is registering a second diagnostic task with `updater.add()` and structuring the check as a separate `_check_*` method.

---

## Answer Key

### Exercise 1

The key subtlety: `diagnostic_updater.Updater` publishes at its own internal rate (default 1 Hz). You do not call `publish` yourself — the updater handles that. You only register check functions and let the updater call them.

`stat.summary()` sets the overall level and message. `stat.add(key, value)` adds `KeyValue` entries — optional but useful for downstream monitoring tools.

The WARN appears within 3 seconds because: the updater polls once per second, and the check condition is `time.monotonic() - self._last_pose_time > 2.0`. Two pose updates will pass (at 0s and 1s) before the 2-second threshold trips on the third updater cycle.

When `turtlesim_node` restarts, `/turtle1/pose` messages resume within about 0.1 seconds. On the next updater cycle (within 1 second), the check sees a recent pose and returns OK.

### Exercise 2

There are multiple valid designs. One clean approach:

```python
from rclpy.parameter_client import AsyncParameterClient

# in __init__:
self._param_client = AsyncParameterClient(self, '/turtle_lf_controller')
self._kv = None
self.create_timer(2.0, self._poll_kv)
self._updater.add('Kv Bounds', self._check_kv)

def _poll_kv(self):
    future = self._param_client.get_parameters(['Kv'])
    future.add_done_callback(
        lambda f: setattr(self, '_kv', f.result().values[0].double_value if not f.exception() else None)
    )

def _check_kv(self, stat):
    if self._kv is None:
        stat.summary(DiagnosticStatus.STALE, 'Kv not yet polled')
    elif self._kv <= 0 or self._kv > 5.0:
        stat.summary(DiagnosticStatus.WARN, f'Kv={self._kv:.2f} out of range (0, 5]')
    else:
        stat.summary(DiagnosticStatus.OK, f'Kv={self._kv:.2f} OK')
    return stat
```

## Summary

| Concept | Key point |
|---|---|
| `/diagnostics` | Standard topic for node health reports; type `diagnostic_msgs/msg/DiagnosticArray` |
| `DiagnosticStatus.level` | 0=OK, 1=WARN, 2=ERROR, 3=STALE |
| `Updater` | Manages periodic publication; call `updater.add()` to register tasks |
| `stat.summary(level, message)` | Sets the status level and short description |
| `stat.add(key, value)` | Adds `KeyValue` detail entries |
| `package.xml` | Must include `<depend>diagnostic_updater</depend>` |
