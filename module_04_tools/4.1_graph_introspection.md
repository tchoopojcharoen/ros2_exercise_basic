## The Gap in rqt_graph

You used `rqt_graph` in section 1.10 to see nodes and topics as a live diagram. That was a bird's-eye view. In this section you drill deeper: the graph shows structural connectivity — names that matched — but it cannot tell you whether data is actually flowing.

Consider this scenario: a publisher and a subscriber are both on `/turtle1/pose`, and `rqt_graph` shows an arrow between them. That means their topic names match. It does not mean:

- The subscriber's QoS policy is compatible
- The publisher is actually sending data at the expected rate
- The subscriber is processing the messages it receives

The three tools in this section — `rqt_topic`, `rqt_service_caller`, and `ros2 node list --include-hidden` — fill those gaps.

---

## rqt_topic

`rqt_topic` is a GUI topic browser. It lists all active topics and lets you subscribe to selected ones, showing live field values as they arrive. It is faster to explore than `ros2 topic echo` and easier to watch multiple fields simultaneously.

```bash
rqt_topic
```

**Interface:**

- The topic list shows the topic name, type, and current publish rate
- Check the checkbox next to any topic to subscribe and watch values
- Expand a topic row to see individual fields; values update in place
- A field stuck at `0.0` or `N/A` when you expect movement means: either the publisher has stopped, or data is arriving but not matching (wrong QoS)

The key diagnostic insight: `ros2 topic echo` shows that data is arriving *somewhere*. `rqt_topic` shows whether it is arriving *at this subscriber*. If `rqt_graph` shows an arrow but `rqt_topic` shows a stuck value, the connection is structural (names match) but no data is flowing to this particular subscriber.

## rqt_service_caller

`rqt_service_caller` lets you call any ROS2 service interactively using a GUI form. You do not need to type a YAML request string at the command line.

```bash
rqt_service_caller
```

**Workflow:**
1. Select a service from the dropdown at the top
2. Click the **Refresh** button if the service is not listed (services only appear after nodes start)
3. Fill in the request fields in the tree editor — click a value to edit it in place
4. Click **Call** to send the request
5. The response appears in the Response section at the bottom

This is the fastest way to prototype service calls, adjust parameters, and verify a service is reachable before writing the code that calls it.

## Hidden Nodes

Run this when the system is idle (only `turtlesim_node` running):

```bash
ros2 node list --include-hidden
```

Compare the output to `ros2 node list` (without the flag). You will see one or more entries like `/_ros2cli_1234`. These are **transient CLI processes** — they are the `ros2 topic echo`, `ros2 topic hz`, and similar commands you run in other terminals. Each one registers as a node while it is running and disappears when it exits.

These nodes appear in `rqt_graph` (they look like extra subscribers or publishers). Beginners are sometimes confused by them — the arrow from `/turtle1/pose` to `/_ros2cli_3271` is the `ros2 topic echo /turtle1/pose` command you ran in another terminal. When the command exits, the arrow disappears.

**Practical rule:** if you see an unexpected `/_ros2cli_*` node, check whether someone ran a CLI command recently. It is not a bug.

## Answer Key

### Exercise 1

1. `/turtle1/cmd_vel` carries velocity commands (visible in `ros2 topic list`; the `turtle_controller` publishes it and `turtlesim_node` subscribes).
2. `turtle_controller` — it subscribes to `/turtle1/goal`. When `goal_point_publisher` disappears, the last goal remains in memory but no new ones arrive. The turtle stops after reaching the last goal.
3. One publisher on `/turtle1/pose` — `turtlesim_node`.
4. After killing `goal_point_publisher`, rqt_graph shows an arrow from `/turtle1/goal` pointing to `turtle_controller` with no publisher node at the other end. This is an orphaned subscriber.

**Key distinction:** The arrow is still drawn because the *subscription* is still active (`turtle_controller` is still running and subscribed). The arrow shows the structural connection, not a live data flow. `rqt_graph` cannot show you that the publisher side is gone until you refresh — and even then it only shows that no publisher node is visible, not that the last message was stale.

### Exercise 2

Disabling the controller via the `/controller_enabled` service stops it from publishing. The `/turtle1/cmd_vel` topic remains *registered* (you can still see it in `ros2 topic list`) but no new messages arrive — which is why rqt_topic shows a silent topic rather than disappearing.

For `rqt_service_caller`, the `/turtle1/set_pen` service accepts an `r`, `g`, `b`, `width`, `off` request. Any values work as long as `off=0` (pen is on). There is no response body — the call succeeds silently.

## Summary

| Tool | What it shows | What it cannot tell you |
|---|---|---|
| `rqt_graph` | Which names are connected (structural) | Whether data is flowing, QoS compatibility |
| `rqt_topic` | Live field values as they arrive | Whether the publisher logic is correct |
| `rqt_service_caller` | Service reachability + request/response | Whether the service logic is correct |
| `ros2 node list --include-hidden` | All nodes including transient CLI processes | None — this is the full list |

**The structural / data-flow distinction** is the most important idea in this section. Every later section (QoS mismatch in 4.3, TF errors in 4.6, the capstone in 4.9) relies on it: the graph can look connected while data is not flowing.
