## Headers: stamp and frame_id

Many ROS2 message types include a `std_msgs/msg/Header` field at the top:

```
std_msgs/msg/Header
  builtin_interfaces/msg/Time stamp
    int32 sec
    uint32 nanosec
  string frame_id
```

- **`stamp`** — when the data was acquired (e.g., when the sensor read the value). This is the acquisition time, not the time the message was published. The difference matters for latency measurement and sensor fusion.
- **`frame_id`** — the coordinate frame in which the data is expressed (e.g., `"camera_link"`, `"base_link"`, `"map"`). Every measurement belongs to a frame; without `frame_id`, you cannot transform sensor data between frames. You will use this in 4.6 when working with TF2.

To check whether a message type has a header:

```bash
ros2 interface show turtlesim/msg/Pose
ros2 interface show geometry_msgs/msg/PoseStamped
```

`turtlesim/msg/Pose` has no header — it is just `x`, `y`, `theta`, `linear_velocity`, `angular_velocity`. `geometry_msgs/msg/PoseStamped` wraps a `Pose` in a `Header`, which is why it is called "Stamped".

## ros2 topic delay

`ros2 topic delay` measures end-to-end latency: the time between a message's `header.stamp` and the moment the tool receives it. It requires the message type to contain a header.

```bash
ros2 topic delay /turtle1/pose
```

Run this now. You will see:

```
average delay: not applicable
```

This is expected: `turtlesim/msg/Pose` has no `header.stamp`. The tool cannot compute latency for a message that carries no timestamp.

Try it on a topic that does have a header:

```bash
ros2 topic delay /tf
```

`tf2_msgs/msg/TFMessage` contains `geometry_msgs/msg/TransformStamped`, which has a header. If any TF publishers are running, `ros2 topic delay /tf` will show real latency numbers.

**When you see "not applicable":** The topic is either not stamped, or the node is not publishing `header.stamp`. This is not a bug in `ros2 topic delay` — it is information about the message design. If you are writing your own messages and need latency measurement, always include a `Header`.

## use_sim_time and /clock

When nodes are in simulation mode, they replace the system wall clock with a `/clock` topic:

```bash
ros2 param get /NODE_NAME use_sim_time
```

If `use_sim_time` is `True`, the node reads time from `/clock` instead of the system clock. This is important during bag playback: if you record a bag with timestamps and play it back faster or slower than real time, nodes with `use_sim_time: True` will see the correct elapsed time for the recorded events, while nodes using wall time will be out of sync.

For the turtlesim exercises in this tutorial, `use_sim_time` is `False` (default). You would set it to `True` in a full simulation environment like Gazebo, where a simulation clock is published.

Diagnostic: if you are playing back a bag and nodes seem to have wrong timestamps:

```bash
ros2 topic hz /clock   # should be nonzero during playback
ros2 param get /YOUR_NODE use_sim_time
```

## QoS Mismatch: The Four-Step Diagnosis Workflow

A QoS mismatch is a communication failure that `rqt_graph` cannot detect. The graph shows an arrow (names match), but data never arrives. You diagnosed this intuitively in section 2.7. Here it is as a repeatable four-step procedure.

**Symptom:** A subscriber receives no messages even though a publisher exists.

### Step 1 — Confirm the topic exists

```bash
ros2 topic list
```

Verify the topic name is present. A typo means the topic does not appear at all — that is not a QoS mismatch, it is a naming error.

### Step 2 — Confirm rqt_graph shows a connection

Open `rqt_graph`. Confirm there is an arrow from the publisher node to the subscriber node for this topic. If no arrow is present, the subscriber's topic name does not match the publisher's — again, a naming error, not a QoS mismatch.

### Step 3 — Confirm data is leaving the publisher

```bash
ros2 topic echo /TOPIC_NAME
```

If `ros2 topic echo` receives data, the publisher is working. If it does not, the publisher itself is the problem (it may not be running, or not publishing). `ros2 topic echo` uses a BEST_EFFORT subscriber — it will receive turtlesim Pose messages even if your node's subscriber does not.

### Step 4 — Check matched publisher count

```bash
ros2 topic info --verbose /TOPIC_NAME
```

Look at the Subscription section for your node. If `Matched Publishers: 0`, the subscriber exists but no publisher's QoS is compatible with it. Compare the `Reliability` and `Durability` fields between the publisher and subscriber sections.

The most common mismatch in turtlesim:

| Publisher (turtlesim) | Your subscriber | Result |
|---|---|---|
| Reliability: BEST_EFFORT | Reliability: RELIABLE | No match — subscriber gets nothing |
| Durability: VOLATILE | Durability: TRANSIENT_LOCAL | No match |

Fix: use `QoSPresetProfiles.SENSOR_DATA.value` for sensor topics, or match the publisher's policy exactly.

## Exercise 2 — QoS Mismatch Diagnosis

**Description**

Write a minimal `PoseListenerBroken` node that subscribes to `/turtle1/pose` with the wrong QoS. Then use the four-step workflow to diagnose it.

**Template — `pose_listener_broken.py`:**

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy
from turtlesim.msg import Pose


class PoseListenerBroken(Node):
    def __init__(self):
        super().__init__('pose_listener_broken')
        qos = QoSProfile(
            depth=10,
            reliability=ReliabilityPolicy.RELIABLE,  # wrong for turtlesim
        )
        self.create_subscription(Pose, '/turtle1/pose', self._on_pose, qos)
        self.get_logger().info('PoseListenerBroken started — waiting for pose...')

    def _on_pose(self, msg):
        self.get_logger().info(f'Pose received: x={msg.x:.2f}')


def main():
    rclpy.init()
    rclpy.spin(PoseListenerBroken())
    rclpy.shutdown()
```

1. Save this file anywhere on your machine (not in your package — it is a throwaway node). Run it directly:

   ```bash
   python3 pose_listener_broken.py
   ```

   You should see the start message but **no pose messages**.

2. Execute the four-step diagnosis:
   - Step 1: `ros2 topic list` — confirm `/turtle1/pose` exists
   - Step 2: `rqt_graph` — confirm arrow from `turtlesim` to `pose_listener_broken`
   - Step 3: `ros2 topic echo /turtle1/pose` in another terminal — confirm data is flowing
   - Step 4: `ros2 topic info --verbose /turtle1/pose` — find the subscriber with `Matched Publishers: 0`

3. Fix the QoS:
   ```python
   from rclpy.qos import QoSPresetProfiles
   qos = QoSPresetProfiles.SENSOR_DATA.value
   ```
   Restart the node. Confirm pose messages now appear.

**Verification**

- Before the fix: `ros2 topic info --verbose /turtle1/pose` shows a subscription with `Matched Publishers: 0` alongside the working subscription (from `turtle_controller`)
- After the fix: "Pose received: x=..." lines appear in the terminal

## Answer Key

### Exercise 1

`/turtle1/pose` publishes at a fixed rate (approximately 62 Hz) regardless of turtle movement. The turtlesim simulator runs its own physics loop at a fixed frequency — it publishes pose on every tick, whether or not the turtle moved.

`/turtle1/cmd_vel` rate changes because `turtle_controller` only publishes when its control timer fires. At idle (turtle at goal), the controller may still publish at the control frequency (depending on your implementation), but the velocity values are zero or near-zero. During navigation, the rate matches `control_loop_frequency` and values are nonzero.

`ros2 topic delay /turtle1/pose` returns "not applicable" because `turtlesim/msg/Pose` has no `std_msgs/msg/Header`.

### Exercise 2

The mismatch: turtlesim publishes `/turtle1/pose` with `Reliability: BEST_EFFORT`. A subscriber requesting `Reliability: RELIABLE` is more demanding — the publisher cannot guarantee it, so ROS2 refuses the match. The subscriber shows `Matched Publishers: 0` even though an arrow appears in `rqt_graph` (the arrow represents a name match, not a policy match).

After changing to `QoSPresetProfiles.SENSOR_DATA.value` (which uses `BEST_EFFORT` reliability), the subscriber matches and receives messages.

## Summary

| Tool / Concept | Key point |
|---|---|
| `header.stamp` | Acquisition time; required for `ros2 topic delay` |
| `frame_id` | Coordinate frame the data is in; required for TF transforms |
| `ros2 topic delay` | Measures stamp-to-receipt latency; only works on stamped messages |
| `use_sim_time` | When `True`, nodes use `/clock` instead of wall time |
| QoS mismatch | Graph arrow = names match; `Matched Publishers: 0` = policies incompatible |
| Four-step workflow | `topic list` → `rqt_graph` → `topic echo` → `topic info --verbose` |
